# Архитектура

1. **Получение кандидатов.** Три TF-IDF канала: символьные n-граммы заголовка, словные n-граммы заголовка и словные n-граммы описания. Четвёртый канал — базовая `intfloat/multilingual-e5-base` в локальном INT8 ONNX-инференсе (Модель не дообучалась, из-за ограничения в ресурсах (нет дискретной gpu с cuda)).
2. **География.** Поиск ведётся глобально и внутри точной либо восстановленной по train локации объявлений.
3. **Реранжирование.** `HistGradientBoostingClassifier` выбирает 50 объявлений из объединённого пула. Он использует ранги каналов, cosine similarity E5, географическую историю, пересечение слов заголовка и запроса, рейтинг, цену, признаки связи и совпадения параметров запроса с параметрами объявления.

Для E5 используются префиксы `query:` и `passage:`. Документ состоит из заголовка (до 40 токенов) и параметров объявления (до 56 токенов); описание обрабатывается отдельным TF-IDF каналом. 

# Проверка качества

Строки train группируются по полному набору полей `search_*`, чтобы одинаковые запросы не попадали одновременно в обучение и проверку. Итоговый скор составил на локальных тестах Recall@50 **0,781821** и **0,786416** на двух независимых срезах по 2 452 query-группы.

# Какие данные и признаки использовались и почему
Для каждого объявления использовались заголовок, описание, параметры,
локация, категория, цена, рейтинг, число отзывов и признаки доступности способов
связи. Для запроса использовались текст запроса, локация, параметры поиска,
категория и признак поиска с доставкой.
Дополнительно применялись dense-эмбеддинги предобученной модели
`intfloat/multilingual-e5-base`.
# Как проверял качество решения
Для локальной оценки формировались срезы по 2 452 query-группы — столько же,
сколько запросов содержалось в benchmark. Учитывалось соотношение запросов с
ранее встречавшимся текстом и новых текстов, поскольку качество на этих группах
заметно различается.
Recall@50 вычислялся как доля известных релевантных
объявлений, попавших в первые 50 результатов. После этого значения
усреднялись по запросам, чтобы группы с большим числом строк не получали
непропорционально большой вес.
# Ошибки и исправления
1. Случайное разбиение давало утечку. Проблема была устранена группировкой по полному набору полей запроса
и разбиением только целых query-групп.
2. Запросы, текст которых уже встречался в train, решались лучше полностью новых
формулировок. Поэтому качество проверялось отдельно
для warm- и cold-запросов, а validation формировался с близким к benchmark
соотношением этих групп.
3. Неточное совпадение геграфии. Точный поиск только по `search_location_id == item_location_id` терял
релевантные объявления для поисковых локаций, обозначающих регион или группу
городов. Для таких запросов область поиска восстанавливалась по истории
соответствий поисковых и товарных локаций. Для слабой статистики использовался
глобальный поиск, чтобы ненадёжный geo-prior не обрезал правильные объявления.
4. Семантически похожие объявления
e5 находил близкие по смыслу объявления, которые не совпадали по параметрам. Для их различения в HGB (классификатор) были
добавлены географические признаки, пересечение параметров, совпадение чисел,
цена и признаки качества объявления.
